Processing path detail

Path Service Latency SLA Destination Use cases
Hot Lambda ESM < 1 second DynamoDB · SNS · SQS Fraud signals, real-time session state, push alerts
Warm KDA / Flink 1 – 30 seconds S3 Silver · ElastiCache · OpenSearch Windowed aggregations, anomaly detection, feature pipelines
Cold Kinesis Firehose 60 s – 5 min S3 Bronze (Parquet) Archival, batch analytics, historical replay

All three paths are fed simultaneously by the same Kinesis stream. Each registers as an independent consumer — with Enhanced Fan-Out (EFO) giving Lambda and Flink their own dedicated 2 MB/s per shard, fully isolated from Firehose's standard polling throughput.

Layer-by-layer configuration

Sources → Kinesis Data Streams

RDBMS / AWS DMS
  • DMS replication instance streams CDC to Kinesis target endpoint
  • Row-level INSERT / UPDATE / DELETE as JSON events
  • Primary key used as partition key (shard-ordering guarantee)
  • DMS task ongoing replication mode
Application services
  • PutRecords API — up to 500 records / 5 MB per batch
  • SDK retry with exponential backoff on ProvisionedThroughputExceeded
  • Domain event ID as partition key for entity ordering
  • KPL for high-throughput producers with aggregation
IoT / Kafka / logs
  • IoT Core rule action → Kinesis target
  • Kafka → Kinesis via MSK Connect + Kinesis Kafka connector
  • Kinesis Agent for flat file / log tailing on EC2
  • CloudWatch Logs subscription filter → Lambda → KDS

Kinesis shard capacity formula

# Required shards (write side) write_shards = ceil( (records_per_sec × avg_record_bytes) / 1_048_576 ) # Required shards (read side — without EFO) read_shards = ceil( (num_consumers × 2_097_152) / 2_097_152 ) # Read side with EFO — each consumer gets its own 2 MB/s → same as write side read_shards_efo = write_shards # Final provisioned count with 20% headroom shard_count = max(write_shards, read_shards) × 1.2 # On-demand mode: skip this — KDS auto-scales up to 200 shards (400 MB/s write)

Three processing paths

Lambda — hot path config
  • Event Source Mapping with BisectBatchOnFunctionError = true
  • MaximumRetryAttempts = 2
  • Dedicated SQS DLQ for poison-pill events
  • ParallelizationFactor 1–10 per shard
  • Concurrency = shards × parallelization factor
  • EFO recommended for low iterator age
KDA Flink — warm path config
  • Managed Apache Flink (KDA) with EFO consumer
  • RocksDB incremental checkpoints to S3
  • Tumbling window (1 min) + sliding window (5 min)
  • Watermark strategy: bounded out-of-orderness 10s
  • StreamingFileSink → S3 Silver in Parquet + Snappy
  • Parallelism = shard count
Firehose — cold path config
  • Dynamic partitioning on event_type field
  • Inline Lambda transform for field normalization
  • Buffer: 128 MB or 300 s (whichever first)
  • Format conversion to Parquet via Glue schema
  • S3 prefix: s3://bucket/bronze/dt=!{timestamp:yyyy-MM-dd}/
  • Backup bucket for failed records

S3 Bronze → Silver (AWS Glue ETL)

# Glue PySpark job — Bronze to Silver transformation dyf = glueContext.create_dynamic_frame_from_catalog( database="raw_db", table_name="events_bronze", push_down_predicate="dt >= '2024-01-01'", # partition pruning transformation_ctx="source" ) # Apply schema, dedup, type coercion df = dyf.toDF() \ .dropDuplicates(["event_id", "event_ts"]) \ .withColumn("event_ts", col("event_ts").cast(LongType())) \ .withColumn("amount", col("amount").cast(DecimalType(18, 4))) # Write Silver zone — partitioned Parquet with job bookmarks glueContext.write_dynamic_frame_from_options( frame=DynamicFrame.fromDF(df, glueContext, "silver"), connection_type="s3", format="parquet", connection_options={"path": "s3://bucket/silver/", "partitionKeys": ["year", "month", "day"]}, transformation_ctx="sink" )

S3 Silver → Gold (Databricks / EMR)

# Databricks Auto Loader — Silver → Gold Delta merge (SCD Type 2 pattern) df_stream = spark.readStream \ .format("cloudFiles") \ .option("cloudFiles.format", "parquet") \ .option("cloudFiles.schemaLocation", "s3://bucket/_schema/events/") \ .load("s3://bucket/silver/events/") # Merge into Gold Delta table def merge_to_gold(batch_df, batch_id): DeltaTable.forPath(spark, "s3://bucket/gold/dim_events") \ .merge(batch_df, "target.event_id = source.event_id") \ .whenMatchedUpdateAll() \ .whenNotMatchedInsertAll() \ .execute() df_stream.writeStream \ .trigger(availableNow=True) \ .option("checkpointLocation", "s3://bucket/_ckpt/gold_events/") \ .foreachBatch(merge_to_gold) \ .start()

Governance & orchestration

Glue Catalog + Lake Formation
  • One Catalog shared across Athena, Redshift Spectrum, Databricks, EMR
  • Lake Formation column-level grants per IAM role / group
  • Glue Crawler runs post-ETL to register new partitions
  • Schema registry for Avro / JSON schema evolution
  • analytics_db Gold tables: PII columns masked for BI roles
Step Functions orchestration
  • GlueStartJobRun → Bronze→Silver ETL
  • GlueCrawler → update Catalog partitions
  • EmrAddStepsTask or Databricks Jobs API → Silver→Gold
  • AthenaStartQueryExecution → data quality check
  • SNS publish on success / failure
  • EventBridge schedule or S3 event trigger
CloudWatch alarms
  • GetRecords.IteratorAgeMilliseconds > 60 000 ms → consumers lagging
  • WriteProvisionedThroughputExceeded > 0 → hot shards
  • Firehose DeliveryToS3.DataFreshness > 900 s
  • Glue driver.aggregate.numFailedTasks > 0
  • Lambda DestinationDeliveryFailures (DLQ) > 0
  • KDA millisBehindLatest > 30 000 ms

Key design decisions & trade-offs

Shard strategy
  • Use on-demand mode unless exceeding 200 shards or needing fine-grained cost control
  • Partition key entropy is critical — never use a low-cardinality key like event_type alone
  • Composite keys: customer_id + event_type for ordering + distribution
  • Monitor GetRecords.IteratorAgeMilliseconds as the primary throughput health signal
EFO vs shared throughput
  • Use EFO for any consumer where latency SLA < 5 s
  • Standard polling: 5 consumers × 2 MB/s = 400 KB/s each at 10 shards
  • EFO: each consumer gets full 2 MB/s per shard — 5× improvement
  • EFO adds ~$0.015/shard-hour — worth it for Lambda and Flink hot/warm paths
Firehose vs direct S3 write
  • Firehose handles Parquet conversion, S3 buffering, and delivery retries natively
  • Direct KDS → Lambda → S3 gives lower latency but requires custom buffering logic
  • Firehose dynamic partitioning replaces a Bronze Glue job for simple cases
  • Firehose max throughput: 1 GB/s — sufficient for most ingestion loads
